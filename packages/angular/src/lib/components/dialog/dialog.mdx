## Overview

Enhanced modal dialog that extends the native HTML `<dialog>` element with built-in animations, composition components, and accessibility features.

### Features

- **Native HTML Dialog**: Built on the standard dialog element with full semantic support
- **Three-row layout**: Pinned header and action row with a scrolling body, on a surface that stays content-sized
- **Smooth Animations**: Automatic fade transitions for open/close states
- **Composition Components**: Optional `DialogHeader` and `DialogButtons` for consistent layouts
- **Programmatic Control**: Open/close methods plus show property binding
- **Backdrop Handling**: Click-outside-to-close with customizable behavior
- **Accessibility**: Full keyboard navigation, focus trapping, and screen reader support

## The three rows

The surface is a flex column of three rows, and **only the middle one scrolls**:

- **Header** — `[dialog-header]` (alias `[uni-dialog-header]`): pinned
- **Body** — everything else you project: scrolls
- **Footer** — `[dialog-buttons]` (alias `[uni-dialog-buttons]`): pinned

The dialog itself is `overflow: clip` on **both** axes, so it is never a scroll
container. This is what lets a title and an action row stay put while a long
form moves between them.

Unlike the drawer, which is deliberately viewport-tall, the dialog is **sized by
its content**. It declares no height at all and simply grows, up to
`calc(100dvh - 2 × inset)` — at which point the body starts to scroll. The
`inset` theme option is that gap from the viewport edge (`lg`, 32px, by
default).

The three rows must be **direct children** of the `<dialog>`. Wrapping them in a
sizing div puts the whole group into the body row, where nothing is pinned — put
the width on the dialog itself instead.

### Padding

Two options, because the two rows want different things:

- **`padding`** — the whole surface. All three rows sit inside it, which is what
  makes the default header read as a pill floating in the dialog.
- **`bodyPadding`** — the scrolling row alone.

Padding on the surface is safe here (it is not safe on a box that scrolls)
precisely because the dialog never scrolls: only its body row does.

<div class="tip">

Setting one overflow axis computes the other to `auto`. If you write your own
surface, always set both — a single `overflow-x: hidden` is enough to turn a
container into an accidental scroller.

</div>

Do not measure this with `dialog.scrollHeight === dialog.clientHeight`. Under
`overflow: clip` Chrome still reports a descendant's layout overflow in the
surface's `scrollHeight`, reaching through the body's own scroll container, so
that equality holds only while the body is short enough not to scroll. The
invariant that actually holds is that the dialog cannot be scrolled: set
`scrollTop` on it and it stays at `0`.

### A long form

The three rows in action: the title and the actions hold their place while the
form between them scrolls. Nothing in the markup asks for this — projecting a
`[dialog-header]` and a `[dialog-buttons]` is enough.

### A short dialog

The same dialog, sized by its content. It only starts scrolling once it reaches
`inset` from the viewport edge, so a confirmation stays as small as its message.

<StoryExample of={Stories.ShrinkToContent} />

### Without a header

With no `[dialog-header]` to be labelled by, name the dialog with `ariaLabel`
and let `defaultCloseButton` render the floating close in the corner.

<StoryExample of={Stories.WithoutHeader} />

### Controlled by `show`

`[(show)]` is two-way, so state outside the template can open and close the
dialog; `(showing)` reports back, emitting `false` only once the closing
animation has finished.

## Best Practices

**Use for:** Important notifications, confirmations, user input forms
**Avoid:** Non-critical information, nested dialogs, complex navigation

## Accessibility

Built on the native `<dialog>` element for automatic ARIA support. Includes:

- Focus trapping and keyboard navigation (Tab, Escape, Enter)
- Screen reader announcements
- Semantic dialog roles
