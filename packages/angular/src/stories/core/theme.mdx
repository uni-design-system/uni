## Overview

A theme is one plain object — the `UniTheme` contract — and everything a
component renders resolves from it by **token name**. Nine fields:

- `id`, `name` — identity; `name` is what theme switchers display.
- `colors` — the **sole color source of truth**. Every other color-bearing
  token derives from it.
- `typography` — the numeric type scale; CSS-ready typefaces are derived on
  read — see [Typography](?path=/docs/core-typography--typography).
- `borders` — named border shorthands, derived from `colors` (plus any
  overrides).
- `radii` — corner radius scale, `none` → `max`.
- `shadows` — named elevation shadows.
- `spacing` — the spatial scale, `none` → `xl`.
- `thicknesses` — line weights: `thin`, `standard`, `thick`.
- `motion` — shared overlay timing: `popup` and `panel`.
- `icons` — icon primitives as data-URI masks — see
  [Iconography](?path=/docs/core-iconography--iconography).
- `components` — per-component theming: a fixed base, state-aware `variants`,
  `sizes`, and named `options` that re-point the token scales above.

## Creating a theme

`createTheme({ id, name, colors, … })` is the assembly line, and **colors is
the only required raw material**: borders and the color-bearing parts of
`components` are built from it (`buildBorders`, `buildComponents`), typography,
spacing, and thicknesses come from the shared base scales, radii and shadows
take the base set unless overridden, and `icons` merge over `BaseIcons`.
`createThemeFromPalette` goes one step earlier — a seed + scheme + category
generates the `colors` record itself, which is how the Theme Builder and the
custom brand flow produce complete themes from a single brand color.

Themes register in the `UNI_THEMES` injection token and apply through
`ThemeService.selectTheme()`; every token below re-resolves live when the
theme changes — try the toolbar.

## Validation & runtime registration

Every theme write is validated against the structural contract in uni-core:
`parseTheme(input)` collects **every** issue (`{ path, message }`, e.g.
`colors.primary is required`) instead of letting a malformed theme render as
silent `undefined` CSS; `assertTheme` is the throwing variant. The required
token sets (`REQUIRED_COLOR_TOKENS`, `REQUIRED_TEXT_ROLES`, …) are exported
for tooling. Because a `UniTheme` is plain serializable data, the same
contract validates a theme fetched as JSON — the basis for theme distribution
and generative-UI flows.

The registry is live: `ThemeService.registerTheme(theme, { select? })` adds a
validated theme (it appears in `themeOptions` and `uni-theme-switch`
immediately), `unregisterTheme(id)` removes it, and `setTheme(theme)`
validates and applies without registering. `ThemeService.theme` is a readonly
signal — all writes funnel through these validated paths.

### Applying a theme fetched at runtime

A theme can therefore arrive as data and be applied without a build step —
from the `generate-runtime-theme` / `get-runtime-theme` MCP tools, or the
theme registry the MCP server hosts:

```ts
const { themes } = await fetch('https://uni-mcp.onrender.com/themes/DarkTheme.json').then((r) => r.json());
const result = themeService.registerTheme(themes[0].theme, { select: true });
if (!result.success) console.warn(result.issues);
```

Those payloads omit the built-in icon set — it is roughly 71% of a serialized
theme, and every uni-core consumer already ships it. `registerTheme` and
`setTheme` restore it on the way in, applying the same `{...BaseIcons,
...icons}` rule `createTheme` uses, so a theme's own icons still win. Outside
Angular, call `hydrateTheme()` from uni-core yourself.

## Motion

Overlay timing is a token, not a component detail: every trigger-anchored
panel in the library points at the same named primitive, so retiming them is
one edit rather than a hunt through components.

Two tokens, because two things genuinely move differently — a small panel
attached to a control snaps, a larger free-floating surface settles:

| Token    | Default              | Used by                                             |
| -------- | -------------------- | --------------------------------------------------- |
| `popup`  | 100ms linear, ×0.8   | dropdown, menu, multi-select, combobox, search-input, tag-input, time-input |
| `panel`  | 250ms ease           | popover, callout                                    |
| `reveal` | 350ms ease-in-out    | expand, expand-toggle                               |

`reveal` is a *base* speed rather than a final duration: `uni-expand` scales it
by content height (√-of-height, clamped) so a short region stays snappy and a
tall one isn't rushed, and `uni-expand-toggle` reads the same token so the
chevron turns on the region's clock.

A token carries `duration` (ms), `easing` (any CSS easing function) and an
optional `scale` for panels that grow into place. Slow every popup down, and
soften its curve to match, in one place:

```ts
createTheme({
  id: 'Calm',
  name: 'Calm',
  colors,
  motion: { popup: { duration: 240, easing: 'ease-out', scale: 0.95 } },
});
```

Tokens you don't restate keep their base values, and components may point at
a token of their own — `components.dropdown.options.motion` — so one panel can
differ without forking the scale.

`callout` and `expand` previously carried their own `transitionMs` and
`transitionSpeed` options. Both still work and still win over the token, so a
theme that set them keeps its exact timing; they are deprecated and go away
next major.

Motion is always behind `prefers-reduced-motion` where a component applies it
through `motionSafe`: a theme sets how things move for people who want
movement, never whether they move at all.

## Component theming

Each entry in `components` layers on the scales above: `fixed` styles always
apply, `variants` restyle by state or emphasis, `sizes` scale dimensions, and
`options` are the named knobs a theme re-points (a typeface token here, a
radius token there) — every component docs page lists its own under **Theme
options**. This is what makes re-theming a token swap instead of a stylesheet
edit.
